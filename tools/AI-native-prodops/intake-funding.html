Where development ideas come from, and how they get funded

The nine tools on this site start from an initiative someone has already chosen. This page covers what happens before and around that: where ideas for development come from, how they're sorted, and how each kind of work gets funded. I'm designing it as a lightweight, Kanban-based alternative to scaled agile frameworks, with AI assisting four things: inputs, the workflow, verification, and support after release. It's a proposal, and the toolchain changes it calls for aren't built yet.

Scope

One portfolio, one value stream. Every portfolio is built around a single value stream with its own architecture, applications, teams and business concerns. Each portfolio runs this framework separately, with its own intake, lanes, funding gates and capacity split.

Some architecture spans portfolios. Everyone uses Jira, and most portfolios share enterprise front-end and back-end technology such as identity, a design system, the data platform and cloud infrastructure. I group those into six shared platform portfolios, each funded on its own, shown at the bottom of the diagram.

The framework on one page

Ideas come in at the top, get sorted once, and land in one of three places. Both funded lanes draw on the same delivery teams.

Five input families

A source can start work, add evidence to work already moving, or both. The full list is below.

One sort, three exits

The size test is one feature: one to four team-weeks, the toolchain's own feature size. Signals that aren't actionable yet go to the insight pool.

Two funding gates

Invest pays twice. A small amount, fixed before work starts, buys discovery. A large amount buys the build, after discovery has sized it.

A standing run budget

Run work is ordered continuously against a fixed share of capacity, with no business case per ticket.

AI drafts and people decide at each of the four points. Code recomputes every number a draft states, so a model's figures are never taken on trust.

Invest lane: pay to learn, then pay to build

A large initiative gets two funding decisions. The first is small and fixed before work starts. It pays for the UX research, architecture and proof of concept needed to size the second, which is large.

  1. Gate 1 · $

    Fund discovery

    Two to eight weeks, sized to the unknowns, with a small team: a designer, an architect, one or two engineers and a product manager. The length is set at the gate and holds, so the cost is known before anyone approves it.

  2. 03b · Validate

    Test the riskiest assumptions

    Initiative Intake (03) already records each epic's riskiest demand, feasibility and viability assumptions. Discovery tests them.

  3. Readout

    Proceed, pivot or stop

    Scope in and out, an estimate range, the architecture runway, and the risks that remain. Stopping here is a good outcome, because the loss is small and known.

  4. Gate 2 · $$

    Fund the build

    The business case (04 Justify) is built on the readout and ranked (05 Rank). Money is released milestone by milestone from the roadmap (06 Schedule), so each release is a checkpoint.

A note for finance

The budget lane and the accounting treatment are separate questions. Invest is planned as CapEx. Under US GAAP for internal-use software, FASB's ASU 2025-06 starts capitalization once management has authorized and committed to funding a project and it's probable the project will be completed and the software used as intended.1 The threshold isn't met while significant development uncertainty remains, such as unproven functions that coding and testing haven't resolved yet, or significant performance requirements that are still being substantially revised.2

So discovery and proof-of-concept work is usually expensed, and it's also the work that clears the way to capitalize the build. The update applies to annual periods beginning after December 15, 2027, with early adoption allowed.2 Software sold to customers follows different rules, and so do IFRS reporters. Each company's controller makes the call.

  • Run each one as a product, with internal customers, a roadmap, adoption targets, and a supported default path that teams choose because it's easier.
  • Fund centrally and show usage. Billing teams for usage pushes them off the supported path to save their own budget.
  • Expect a larger Run share. Upgrades, license renewals and patching never stop, so platform portfolios usually carry more Run than product portfolios.
  • Keep the list short. Each platform portfolio is another intake queue every value stream depends on. A capability becomes shared when two or more portfolios need it and duplicating it would cost more than coordinating it.

Two more groups usually stay with corporate IT, outside this framework: the digital workplace (chat, email, office suites, laptops) and corporate systems of record (ERP, CRM, HR and finance, often including payments and billing).

Run as a Kanban system

Both lanes are boards with work-in-progress limits. Work moves when the next column has room, and teams deliver in batches of two days to two weeks. There are no planning intervals or release trains.

  • WIP limits set the pace. Each portfolio sets its own WIP limits. A team pulls the next item when a column has room, so there's no fixed plan to defend.
  • Flow metrics. Cycle time, throughput, work in progress and work-item age replace velocity and interval objectives.
  • One replenishment point. The weekly intake review refills the Sorted columns and looks at any item older than the portfolio's usual cycle time.
  • The boards end after release. Invest work stays on the board until its benefits are measured against the plan set at Initiative Intake.

Compared with SAFe Lean Portfolio Management

SAFe's Lean Portfolio Management tackles the same funding problem with more structure. This framework keeps a few of its ideas and drops the rest. The bet is that continuous flow with explicit limits, plus AI-drafted evidence that a person checks, can replace most of SAFe's planning events and role layers.

What it keeps

  • Funding value streams instead of projects
  • A capacity split between kinds of work
  • A size line above which work needs a portfolio decision
  • Learning before the full investment
  • WSJF, which comes from Don Reinertsen's work on product development flow8

What it leaves out

  • Planning Intervals and release trains
  • Big-room planning events
  • New role layers between teams and executives
  • A separate budgeting event; the split is an executive decision for each portfolio

The choices behind it

01

Continuous flow.

Both lanes run as Kanban boards with WIP limits. Teams deliver in batches of two days to two weeks, with no planning intervals, release trains or added roles.

02

The line between Invest and Run is one feature.

One to four team-weeks. It matches the toolchain's own feature size, so the sort uses a unit the tools already understand.

03

Discovery is time-boxed at two to eight weeks.

The first gate picks the length to fit the unknowns: about two weeks for one technical question, up to eight for a new product area. The length holds once it's picked, so the gate approves a known cost.

04

Discovery gets its own step, 03b Validate.

It has its own outputs and its own funding gate. Numbering it 03b keeps every existing step number and link stable.

05

The capacity split belongs to executives.

Each portfolio's executives set its split, and it will differ by portfolio. A new product may run mostly Invest, while a mature one with a heavy support load may carry more Run. The 60/25/15 in the diagram is only a placeholder.

06

Shared platforms are portfolios too.

They're funded on their own, grouped by theme, with the value-stream portfolios as their customers.
