AI-assisted workflow · For evaluators

Evaluate the tools in one sitting

This page is for leaders deciding whether the tools are worth their team's time: Product Management leaders judging the quality of the documents, Product Operations leaders judging consistency and governance, and Delivery Systems leaders judging what lands in their tools. It points you to the three examples that matter most for your role, says what is built and what is only proposed, explains how your data is handled, and ends with an invitation to try the tools with fictional, public, or disguised material.

Positioning

What this is, and what it is not

Nine tools that take one initiative from customer research to a batch plan and a CSV file for Jira's bulk import, each passing its main output to the next inside the browser. AI drafts most of the documents, code runs the checks, and people revise the drafts and record a sign-off at each review point.

It is

  • AI-assisted Product Management that covers three of six Product Operations areas: data collection, feedback management, and roadmap alignment
  • A connected workflow: persona, journey map, intake, business cases, WSJF ranking, roadmap, BRD, backlog, batch plan
  • Structured documents built on standard frameworks: Jobs to Be Done, demand/feasibility/viability assumptions, WSJF, RICE, MoSCoW, Given-When-Then acceptance criteria, and RAID logs
  • Checked in code: requirement coverage, batch load, and dependency order are computed, with visible warnings
  • A feeder for the systems you already use, ending in a CSV file for Jira's bulk import

It is not

  • Full Product Operations: Release Operations (feature flags, beta testing, deployment comms), Enablement and Training, and Performance Analytics are out of scope. See how the work splits between PM and Product Operations ↗
  • A replacement for Jira, Productboard, or Aha!: it drafts and checks the documents those systems track
  • A team workspace: today it is single-practitioner, one browser at a time
  • A finished product: live data connections and scheduled agents are proposals on the Proposed Architecture page, and none are built
  • A black box: the sample runs are captured output (the Business Cases gallery is a worked example), and every computed check shows its work

Data handling

Where your data goes

Your browser, your key, no middleman server

The AI-powered tools call the Claude API directly from your browser using an API key you provide. The key lives in session memory and clears when the tab closes. Your inputs go from your browser to Anthropic's API and back: there is no server of mine in the path, no account, and no database. Tool state and handoffs live in your browser's localStorage.

Want to evaluate without entering a key or any real data? Every tool has a no-key mode, and the sample runs linked above are captured output, so you can judge the documents without typing anything.

More interested in how it is built? The technical notes cover the build system, the shared package, the versioned data contracts between tools, and this same trust boundary from the code's side.

Known limitations

What you should know before you start

Single-practitioner, per-browser
No accounts or shared workspaces. State lives in one browser's localStorage; clearing site data clears your runs. Team workspaces are on the roadmap, with no date.
Jira integration is CSV import only
The workflow ends in a CSV file for Jira's bulk import. A direct write-back is specified but waits until approvals with sign-in and an audit log exist.
Output varies run to run
Drafting is done by a large language model, so two runs on the same input will not be identical. The computed checks (coverage, load, dependency order) are deterministic; the prose is not.
Built and maintained by one person
This is a working prototype built by one practitioner, with no service-level agreement. That's why the beta feedback below matters.
Who I'm looking for

The first cohort is small, on purpose

The first cohort is limited to approximately 5–10 evaluators with experience in one or more of the following: Product Management, Product Operations, Technical Product Management, engineering or delivery operations, business analysis or requirements, architecture/security/QA/UAT review, portfolio prioritization, or Agile delivery/technical program management.

You do not need to endorse the concept. Skeptical feedback is more useful than encouragement.

Appropriate evaluation material

Use fictional, public, or sanitized information only

This is a single-user proof of concept, not a secure or production system.

Use one of these

  • A fictional initiative
  • A public product scenario
  • A realistically disguised initiative, with names and numbers changed
  • The supplied PetHealth scenario

Do not enter

  • Confidential strategy
  • Customer personal data
  • Proprietary financials
  • Source code
  • Security architecture
  • Credentials other than an API key entered into the designated key field
  • Regulated or export-controlled information
Suggested evaluation path

About 60–90 minutes, starting at Initiative Intake

  1. Frame one initiative and two alternatives.
  2. Review the proposed epics and their demand, feasibility, and viability assumptions.
  3. Generate one or two business cases.
  4. Compare the prioritization views and adjust the weights.
  5. Review the roadmap proposal.
  6. Generate the BRD for one funded epic.
  7. Review the backlog and requirement mapping.
  8. Review the batch proposal and Jira CSV.

Starting with the Persona and Journey Map adds approximately 20 minutes. The beta runbook walks each stop in more detail, including what to watch for at every gate.
